## 2. NLQ Planner Boundary Definition

The `NLQPlanner` module (`gods_eye/reasoning/planner.py`) is responsible for converting raw natural language queries (`UserQuery`) into one or more validated `ToolCall` objects.

```
UserQuery (Text)
    │
    ▼
[NLQPlanner Pipeline]
  1. Natural Language Interpretation
  2. Intent Extraction
  3. Entity Extraction (global_id, camera_id, zone_id)
  4. Temporal Interpretation (Relative string -> Unix timestamp range)
  5. Tool Selection (Select 1 of 8 Phase 5.2 tools)
  6. Tool Argument Generation & Schema Validation
    │
    ▼
ToolCall (call_id, tool_name, arguments)
```

**Planner Non-Responsibilities:**
- The planner MUST NOT query databases directly.
- The planner MUST NOT generate evidence or synthesize final reasoning answers.
- Tool calls generated by the planner are dispatched strictly through `ToolDispatcher.dispatch()`.

## 3. LLM Provider Boundary & Fallback Architecture

- **Requirement (§14 Phase 5):** Master Spec §14 Phase 5 specifies an LLM function-calling architecture (stateless per query).
- **Rule 7 & 8 Guardrails:** The LLM MUST NOT become the source of ground-truth memory. It is prohibited from fabricating observations, identities, timestamps, or locations.
- **Hybrid Architecture:** `NLQPlanner` will support an abstract `LLMProvider` interface alongside a deterministic rule-based pattern matching planner (`RuleBasedPlanner`). The `RuleBasedPlanner` ensures 100% offline, deterministic execution for standard query classes during unit testing and offline execution.

**Open Decision:** Selection of production remote LLM provider API client (e.g. Anthropic Claude SDK) vs local model wrapper. (Kept abstract via `LLMProvider` ABC).

## 5. Ambiguity Handling & Schema Validation

- **Ambiguous / Missing Entities:** If a query contains vague terms (e.g., *"Where is he?"*) without an explicit `global_id`, `NLQPlanner` returns an empty `ToolCall` list and triggers `QueryStatus.AMBIGUOUS`.
- **Unsupported Queries:** Queries requesting capabilities outside the 8 tools (e.g. *"Predict trajectory clusters"*) return `QueryStatus.INVALID_QUERY`.
- **Temporal Parsing:** Relative times (e.g., *"in the last 15 minutes"*) are parsed relative to `UserQuery.timestamp_ns`.
- **Schema Impact:** No Phase 5.1 schema changes required.

---

## 6. Pre-Execution Tool Call Validation

Before a `ToolCall` is emitted to `ToolDispatcher`, `NLQPlanner` validates:
1. `tool_name` is one of the 8 approved tools.
2. Mandatory string arguments (e.g. `global_id`, `camera_id`) are non-empty.
3. Timestamp ranges satisfy $start\_ns \le end\_ns$.
4. Invalid `ToolCall` payloads are caught before database execution.

---

## 7. Security & Safety Boundary (§10 Master Spec)

- **Authentication & Scope Enforcement:** Queries require elevated scope (`GODS_EYE_SCOPE=reasoning`).
- **Prompt Injection Defense:** Natural language query strings are sanitized; strings cannot inject SQL or override tool selection logic.
